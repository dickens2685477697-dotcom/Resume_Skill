# 基于 JD 的经历润色

本阶段位于证据匹配之后、简历规划之前。目标不是“把原经历写得更好听”，而是用目标岗位关心的能力和产出来组织已经确认的事实，让招聘者能快速看出这段经历为什么与当前 JD 有关。

## 进入条件

必须同时具备：

- 具体目标岗位的 `jd-analysis.json`；
- 当前岗位的 `evidence-matrix.json`；
- 可回指到项目或经历记录的事实字段；
- 拟写入简历的事实状态为 `verified` 或 `user_confirmed`。

生成时把当前 `evidence-matrix.json` 文件的 SHA-256 写入 `source_evidence_matrix_sha256`。若证据矩阵因新材料、用户确认或 JD 版本变化而更新且摘要不再一致，已有 `experience-tailoring.json` 视为过期，重新执行本阶段。用户只要求润色某一段时，只处理指定记录，但仍使用完整 JD 判断定位和去重。

## 核心原则

### 事实层不变，表达层按岗位变化

通用项目和经历记录保存“发生了什么”；`experience-tailoring.json` 保存“针对这个岗位怎样讲”。岗位定向表达不得回写 `projects/` 或 `experiences/`。

允许调整：

- 选择哪些已确认事实进入 bullet；
- 先写问题、动作、决策、交付还是结果；
- 把事实放在产品、研究、设计、工程、数据或协作视角下表达；
- 使用与 JD 语义一致且事实支持的行业词汇；
- 合并互补事实、拆分多主张长句、删除低相关细节。

不允许调整：

- 新增材料中没有的动作、工具、对象、范围、数字或结果；
- 把参与改成负责，把团队成果改成个人成果，把方案改成上线结果；
- 把目标、估算、baseline 或未来计划写成实际结果；
- 为了命中关键词改变原事实的专业含义。

## 润色流程

### 1. 提炼岗位叙事

从 JD 中先确定，而不是从原简历句子开始改：

1. 岗位要解决的核心问题；
2. 最受重视的 3–5 个能力信号；
3. 招聘方期待看到的工作产出和责任级别；
4. 必须自然出现、但只能在证据支持时使用的术语；
5. 容易误导的近义词或职责升级词。

将这些内容写入 `role_narrative`。关键词只是表达线索，不能作为选择证据的唯一理由。

### 2. 为每段经历确定唯一主叙事

结合证据矩阵，为每项候选记录写一句 `positioning`，说明“这段经历要向该岗位证明什么”。再分配：

- `primary_signals`：本段最重要的 1–2 个能力信号；
- `supporting_signals`：可辅助体现但不抢主线的能力；
- `requirement_refs`：对应的 JD 要求；
- `excluded_evidence`：真实但本岗位不值得占篇幅，或会与其他经历重复的事实。

不同经历应形成互补证据组合。若多段都证明同一能力，明确哪一段承担主证明，其他段换角度或删减。

### 3. 锁定事实片段

先创建 `evidence_selection`，再写句子。每个事实片段必须记录：

- `field_paths`：来源于记录的哪些字段；
- `source_refs`：原始来源定位；
- `evidence_status`；
- `intended_signal`：准备证明哪项能力；
- `ownership`：个人、共同完成或团队结果；
- `measurement_type`：涉及数字时标明实际、目标、baseline 或估算。

一个 bullet 可以组合多个互补事实，但不得把不同时间、范围或责任主体的事实拼成虚假的因果关系。

### 4. 生成岗位定向 bullet

根据证据选择最合适的结构，而不是机械套用 STAR：

- 产品/策略岗位：问题或目标 → 本人判断/动作 → 交付或决策影响；
- 用户研究岗位：研究问题 → 方法与样本 → 洞察 → 如何影响后续；
- 设计岗位：用户或业务约束 → 关键设计决策 → 原型/规范/交付 → 验证；
- 工程岗位：技术问题/约束 → 实现或架构决策 → 系统交付 → 性能、质量或稳定性结果；
- 运营/增长岗位：对象与目标 → 策略/实验 → 执行范围 → 实际结果。

优先写招聘方能判断责任与能力的具体动作。结果证据缺失时，以真实的交付、验证发现、决策采纳或协作产出收束，不用空泛成效词补齐。

每个候选 bullet 写入：

- `bullet_id` 与 `draft`；
- `primary_signal` 与 `requirement_refs`；
- `field_paths`、`source_refs` 与 `evidence_status`；
- `keyword_alignment`：自然采用的 JD 语汇及其事实依据；
- `ownership`；
- `risk_notes`；
- `selection_status`：`selected`、`alternate` 或 `exclude`。

默认只生成一个最佳版本；只有两种表达分别适配不同高优先级要求、且选择会实质影响简历叙事时，才保留少量 `alternate`，不要批量生成同义句。

### 5. 做四项对照检查

逐条比较“原始事实—JD 要求—润色句—来源映射”：

1. **相关性**：读者能否看出它在回应哪项岗位要求；
2. **证据忠实度**：句中每个可核查主张能否回到字段和来源；
3. **责任边界**：动词强度是否符合本人角色，团队结果是否明确边界；
4. **信息增益**：是否包含动作、关键方法/决策、交付或结果，而非只换关键词。

不通过时按“删除无关信息 → 调整角度和顺序 → 降低动词强度 → 排除不安全主张”的顺序修订。不能通过的 bullet 不进入 `resume-plan.json`。

## 词汇对齐规则

可以使用 JD 原词的情形：

- 原词与用户实际工作语义等价；
- 对应行为、交付物或结果已有证据；
- 不会暗示更高职责、更大范围或不同方法。

只保留用户原始说法或改用更弱表述的情形：

- JD 词包含用户未承担的所有权，如“主导”“owner”“端到端负责”；
- JD 词指定了未使用的方法、工具、行业或指标；
- 近义替换会把研究建议写成产品落地、把内部验证写成市场成效。

禁止逐句复刻 JD。若去掉岗位关键词后，bullet 不再包含可验证的个人行为或产出，该 bullet 属于伪匹配，应重写或删除。

## 输出与下游使用

保存 `jobs/<job-id>/experience-tailoring.json`。`resume-plan.json` 的每项 bullet 计划应引用已选择的 `bullet_id`，最终 `resume-source-map.json` 继续使用相同的 `field_paths` 和 `source_refs`。

用户请求“润色经历”但未要求整份简历时，交付润色后的 bullet、对应 JD 能力、主要取舍和风险即可，不强制生成 `resume.md`。用户请求生成定向简历时，本阶段是生成前的必经步骤。
